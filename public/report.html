1. System Overview

Student360 is a full-stack academic management system built on Next.js 16 App Router and Neon serverless PostgreSQL. It demonstrates core RDBMS concepts including normalised schema design, DDL/DML, Views, JOIN queries, PL/pgSQL stored procedures and functions, and server-side ISR caching to minimise database round-trips.

2. ER Diagram

Relationship Summary: One Department → Many Students; One Department → Many Courses; One Student → Many Grades; One Course → Many Grades. The grades table resolves the M:N relationship between Students and Courses.

3. Normalisation (1NF → 3NF)

1NF – First Normal Form

  • All attributes are atomic (single-valued)
  • No repeating groups
  • Every table has a primary key
  • e.g. grades.marks is a scalar NUMERIC, not a CSV

2NF – Second Normal Form

  • In 1NF + no partial dependencies
  • grades(student_id, course_id) composite key → marks depends on BOTH
  • Department name moved out of students into departments

3NF – Third Normal Form

  • In 2NF + no transitive dependencies
  • Grade letter computed by DB (GENERATED ALWAYS) — not stored separately
  • dept code never repeated in students; accessed via FK join

5. DDL – Schema Highlights

-- Generated column: grade auto-computed from marks
CREATE TABLE grades (
  id         SERIAL PRIMARY KEY,
  student_id INT NOT NULL REFERENCES students(id) ON DELETE CASCADE,
  course_id  INT NOT NULL REFERENCES courses(id)  ON DELETE CASCADE,
  marks      NUMERIC(5,2) NOT NULL CHECK (marks BETWEEN 0 AND 100),
  grade      CHAR(2) GENERATED ALWAYS AS (
               CASE
                 WHEN marks >= 90 THEN 'A+'
                 WHEN marks >= 80 THEN 'A'
                 WHEN marks >= 70 THEN 'B+'
                 WHEN marks >= 60 THEN 'B'
                 WHEN marks >= 50 THEN 'C'
                 ELSE 'F'
               END
             ) STORED,
  exam_date  DATE NOT NULL DEFAULT CURRENT_DATE,
  UNIQUE (student_id, course_id)
);

6. SQL Views

v_student_academic

Joins students ⟶ departments ⟶ grades to produce a single flat row per student with CGPA, courses attempted, and backlog count. Used by the dashboard and student list API (ISR cached).

CREATE OR REPLACE VIEW v_student_academic AS
SELECT
  s.id            AS student_id,
  s.roll_no, s.first_name || ' ' || s.last_name AS full_name,
  s.email, s.semester, s.status,
  d.name          AS department, d.code AS dept_code,
  COUNT(g.id)     AS courses_attempted,
  ROUND(AVG(g.marks)::NUMERIC, 2) AS cgpa,
  SUM(CASE WHEN g.grade = 'F ' THEN 1 ELSE 0 END) AS backlogs
FROM students s
JOIN  departments d ON d.id = s.dept_id
LEFT JOIN grades g ON g.student_id = s.id
GROUP BY s.id, d.id;

v_course_stats

Aggregates enrolment count, average/highest/lowest marks per course joined with department info.

7. PL/pgSQL Procedures & Functions

sp_enrol_student (PROCEDURE)

Called from the Grades API via CALL sp_enrol_student(sid, cid, marks). Validates student and course existence, then UPSERTS a grade row.

CREATE OR REPLACE PROCEDURE sp_enrol_student(
  p_student_id INT, p_course_id INT, p_marks NUMERIC
) LANGUAGE plpgsql AS $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM students WHERE id = p_student_id) THEN
    RAISE EXCEPTION 'Student % not found', p_student_id;
  END IF;
  INSERT INTO grades (student_id, course_id, marks)
  VALUES (p_student_id, p_course_id, p_marks)
  ON CONFLICT (student_id, course_id)
  DO UPDATE SET marks = EXCLUDED.marks, exam_date = CURRENT_DATE;
END;
$$;

fn_promote_student (FUNCTION)

Returns a text message indicating whether the student can be promoted to the next semester, checking for pending backlogs (F grades). Updates semester or marks as graduated.

8. DML – Seed Data

The /api/seed endpoint parses lib/schema.sql and executes all statements including INSERT statements for 4 departments, 5 courses, 5 students, and 8 grade records using ON CONFLICT DO NOTHING for idempotent re-seeding.

11. Caching Strategy

⏱️

ISR – 30 s

Students & Courses list pages use Next.js ISR (revalidate = 30). Static HTML served; DB hit only every 30 s.

🔁

Parallel Queries

Dashboard fires 3 SQL queries in Promise.all() — total latency = slowest query, not sum.

🔌

Neon Connection Pool

@neondatabase/serverless uses HTTP + WebSocket pooling — no cold-connection penalty per request.

🗄️

DB Views as Cache

Aggregated views (v_student_academic) centralise JOIN logic; simple SELECT * in routes.

12. UI Architecture

All data-fetching pages are React Server Components (zero JS shipped to client for data). Only the Add Student and Grades forms are client components ("use client") because they need interactivity. Tailwind v4 utility classes are used throughout with no CSS-in-JS overhead.
